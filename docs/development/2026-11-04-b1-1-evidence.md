## Outcome and implemented decisions

The repository now uses Java release 21, Maven Wrapper 3.3.2 selecting Maven 3.9.9, Compiler 3.13.0, Enforcer 3.5.0, and Surefire/Failsafe 3.5.2. The wrapper pins the Maven distribution digest. Windows invocation quotes paths containing `&`; the test helper sets a process-scoped temporary directory suitable for Surefire. The wrapper's mirror-base replacement now preserves the Maven distribution path.

Spring Boot repackaging produces application JARs with the Boot launcher and dependencies. Failsafe loads compiled application classes from the build output directory, preserving application-context discovery after repackaging.

Transaction intake explicitly registers its transaction-ID and correlation-ID utilities in its own configuration. This removes reliance on a misspelled shared-package scan and keeps the composition boundary local to the service. HTTP coverage checks the accepted response, dispatched command fields, and rejection of invalid amounts without publication.

The payment aggregate distinguishes an allocated identity from a created transaction. First creation succeeds for the matching ID; repeated creation and a mismatched identity are rejected. `TransactionCompletedEvent` restores terminal status, completion time, and version during application and replay. Notification routing is derived from the persisted webhook field. Payment processing retains its intermediate processing state until an outcome event arrives.

The SMTP adapter invokes `JavaMailSender.send` before reporting success and retains the existing `false` result on transport failure. The integration test receives the message through a real local SMTP connection and checks its addressing and content. Durable delivery tasks, retries, provider configuration, and notification-service bootstrap remain separate work.

## Container and version-check repairs

Run 14 failed before container startup: Testcontainers' named-pipe client received HTTP 400 while discovering Docker, and both container-dependent classes reported that no valid Docker environment was available. These were setup errors, with no PostgreSQL/Kafka scenario result. The independent unit, HTTP, and SMTP checks remained green.

Run 15 verified the compatibility repair: importing the Testcontainers 1.21.4 BOM before Spring Boot's dependency management selected the intended version. It connected to Docker 29.3.1 on Windows via WSL 2, started Ryuk 0.12.0, and started both `postgres:16.6-alpine` and `confluentinc/cp-kafka:7.6.1`. The Kafka admin client then rejected the test's 20-second API timeout because it was shorter than the configured request timeout. The test now sets request timeouts to 10 seconds and API timeouts to 20 seconds on its admin and consumer clients. Production client settings are unchanged.

Runs 15 and 16 also reproduced a persistence defect. Appending to a new transaction history with expected version 3 succeeded when it should have raised `OptimisticLockingFailureException`. `JdbcEventStore` now reads a missing history as version zero and compares that value with the caller's expected version before inserting rows. Run 18 verified both the exception and the empty history after the rejected write. The Kafka round trip also passed with the corrected client timeouts.

### Event-store coverage boundaries

The PostgreSQL scenarios use test-owned schema and explicit JDBC transactions. The version checks are sequential; simultaneous writers need a concurrency test. The rollback check reads the database after rollback. It does not retry the same aggregate, whose pending events have already been cleared by `TransactionAggregateRepository.save`. The command service also reads the pending events for publication only after that clear. Fixing publication and recovering committed work remains part of the durable delivery milestone.
